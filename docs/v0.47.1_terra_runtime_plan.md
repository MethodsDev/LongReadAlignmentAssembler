## 1. What the Terra probes established (2026-10-30)

Toy workflow `methods-dev-lab/cromwell_machine_type_probe` in workspace
`LRAA_paper_benchmarking_and_applications`, submissions 4f9b4c00 and 558f7171:

- `predefinedMachineType` together with `cpu`/`memory` is allowed. The VM is the named machine,
  even when `cpu`/`memory` are smaller (1 cpu / 2 GiB on c3d-standard-8 got 8 cores, 31 GiB).
- Google Batch rejects the task up front if `cpu`/`memory` exceed the machine:
  `machine_type "c3d-standard-8" cannot satisfy compute_resource cpu_milli:16000 memory_mib:65536`.
- A request equal to the preset's nominal size is accepted (c3d-standard-8 8/32 GiB,
  c3d-highcpu-8 8/16, c3d-highmem-4 4/32, n2d-standard-2 2/8), EXCEPT c3d-highcpu-4 4/8 GiB
  (rejected; 7.5 and 7 GiB accepted). Cromwell reads "8 GB" as 8 GiB too.
- Without `predefinedMachineType`, Cromwell builds a custom **N1** machine
  (`GcpBatchMachineConstraints.scala`; N2/N2D only via `cpuPlatform`), plus a 5% custom-type
  surcharge. Every LRAA Terra run so far was on custom N1 and, for the runner, non-preemptible.
- miniwdl ignores `predefinedMachineType` (warning) and accepts `preemptible` (retry on
  interruption only, so a no-op locally). Without `cpu`/`memory`, miniwdl reserves 0 cpu and
  0 memory for the task (verified with a toy run), so they must stay.

## 2. Changes

### 2a. Machine types, keeping `cpu`/`memory` (all WDLs reachable from LRAA.wdl and LRAA-singlecell.wdl)

Every runtime block gets `predefinedMachineType` NEXT TO its existing `cpu` and `memory`:

```wdl
runtime {
    docker: docker
    cpu: task_cpu                      # = the cores the command uses (see below)
    memory: "~{task_memGiB} GiB"       # <= the machine's RAM
    predefinedMachineType: machine_type
    preemptible: preemptible_tries
    disks: "local-disk ~{diskSizeGB} SSD"
}
```

- Machine choice: Christophe's tier logic (C3D cpu tiers 4/8/16/30/60/90/180, memory tiers;
  highcpu/standard/highmem by GiB per core; N2D 2-vCPU shapes for 1-cpu tiny tasks). Take it from
  the branch's `LRAA_runner.wdl` / `Partition_data_by_chromosome.wdl` (`c3d_cpu_tier`,
  `c3d_mem_tier`, `c3d_effective_cpu`, `c3d_machine_type`).
- The machine must always hold the request: compare in GiB, and for c3d-highcpu-4 either cap the
  `memory:` value at 7.5 GiB or step up to the next shape when the request is 8 GiB.
- `cpu:` must equal the threads the command uses. The branch sets `--cpu_budget` / samtools `-@`
  from `c3d_effective_cpu` (the tier, which can exceed the request). Either put the same number in
  `cpu:` (costs nothing on Terra: same VM) or keep the commands on the requested cpu. Otherwise
  miniwdl reserves fewer cores than a task uses.
- HDD disks become SSD only where the shape needs it. Not verified that C3D rejects HDD; test one
  HDD task in the probe before converting all.
- One shared helper is not possible in WDL 1.0 (no functions); keep the tier block per task, as the
  branch does, but identical text everywhere so it can be checked by grep.

### 2c. Faster tracking merges (identical output)

- `mergeQuantResults` (LRAA.wdl) and `LRAA_merge_trackings` (LRAA-cell_cluster_guided.wdl): replace
  the single-stream Python gzip loop with the branch's per-shard
  `gzip -dcf | grep -av '^#' | (tail -n +2 unless first) | pigz` jobs, concatenated in input order,
  schema check kept, per-shard `ok` markers. Measured 293 s -> 43 s (25 shards, 4 cores) and
  8 min 39 s -> 28 s; decompressed output byte-identical. pigz is in Docker/Dockerfile.base.
- Machine: c3d-highcpu-4 with `cpu: 4` and memory <= 7.5 GiB (see 1).
